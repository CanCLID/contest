# 粵拼打字比賽「比賽中實時排名顯示」調研報告

> 調研日期：2026-10-22。方法：子代理網絡調研（產品盤點 + 行為經濟學/遊戲化研究 + 技術架構）。
> 狀態：調研結論，供賽事方確認；已整理入 SPEC.md §6.5。第一版暫維持「比賽中只顯示自己數據」。

**一句話結論**：**第一版維持「比賽中只顯示自己數據」是正確的，但不應止於此。** 有充分證據支持加入「低頻、局部、可追趕」的比較資訊（自己的百分位區間、本組前 N 名、與上一名次的差距），而精確全場名次與他人逐字進度應該留到完場。核心矛盾是：**競爭感來自比較，但大池子（2,000 人）的精確名次對 95% 的參賽者是打擊而不是激勵**。

## A. 現有產品實時排名設計盤點

| 產品/場景 | 比賽中顯示什麼 | 更新頻率 / 參考組 | 設計取向 |
|---|---|---|---|
| **TypeRacer** | 賽道上各人「車」的實時位置與進度條、對手頭像/用戶名、自己實時 WPM | 逐字即時；**同場最多約 10 人**，按 WPM 分層配對 | 實時對手進度**只在同級小池**內，不給全站名次 |
| **Nitro Type** | 打字驅動賽車，實時看到對手超前/落後 | 逐字即時；同場數人 | 把排名變成可視覺化的「距離」，非數字名次 |
| **Monkeytype** | 實時只顯示**自己的** live WPM / 準確度 / burst | 每秒更新自己；榜單非即時 | 極簡、無比賽中比較 |
| **Kahoot** | 主持大屏：**每題之間顯示 Top 5**；玩家手機：自己的分數 + **全體名次** + 連對 streak | 每題一次；單場上限 2,000 人；世界紀錄 4,092 人 | **他人只給前 5，精確名次只給自己** |
| **Quizizz / Wayground** | 每題後顯示排行榜（可設匿名）；學生看自己分數與名次；老師可整體關閉 | 每題一次 | 排行榜是**可開關的選項** |
| **Duolingo Leagues** | 每週約 30 人小池，XP 排名實時更新、升班/降班；可整個關掉 | 實時更新，每週重置 | 小參考組 + 定期重置；**不顯示全球排名** |
| **Lichess Arena** | 錦標賽排名**實時更新**的公開榜 | 對局結束即更新；一場可數千人 | 大型即時榜可行（純文字、低頻事件） |
| **Codeforces** | 比賽期間**全公開**實時榜，包括「每題有多少人解出」 | 提交即更新 | 選手會用「各題解出人數」做策略決定 |
| **ICPC** | 賽中實時榜，但**最後 30–60 分鐘凍結**（scoreboard freeze） | 凍結期不更新 | 用「隱藏資訊」製造懸念與防止尾段互相跟隨 |
| **Kaggle** | 實時公開榜（部分測試集計分），最終名次用私榜 | 提交即更新 | 實時榜提升產出，但也是「落後者退出」的來源 |
| **Boston Marathon** | **觀眾**用 app 追蹤最多 10 名跑手、精英實時榜、分段點更新；**跑手比賽中看不到全場名次** | 分段點更新 | 分層：實時比較給觀眾，不給正在比賽的人 |
| **Zwift** | 賽中顯示自己名次、前後車手、時間差、W/kg | 實時 | 只給「附近的人 + 差距」，非全榜 |
| **Gran Turismo 7** | 名次指示器只顯示**前 2 名 + 後 2 名**及時間差 | 實時 | **局部窗口 + 差距**，而非完整榜單 |
| **Strava Live Segments** | 與自己的 PR / KOM 比較 | 實時 | 自我比較，非全站名次 |
| **UCI 職業單車** | 規則禁止對車手使用無線電通訊；車手靠大會黑板得知時間差 | — | 資訊不對稱本身被視為比賽公平性設計的一環 |

**共同模式**：沒有一個大型產品在比賽中給參賽者「全場精確名次」。做法係：（1）實時比較只在**小池或局部窗口**；（2）他人資訊**只給前 N**；（3）精確名次**只給自己**；（4）資訊**可選擇關閉**；或（5）直接**凍結**。

## B. 研究與案例：提升動機 vs 打擊士氣

### 支持實時比較的證據

- **Blanes i Vidal & Nossol (2011, Management Science)**：德國倉務員，只私下告知「你在薪資/生產力分佈的排名」（無任何金錢後果）→ 生產力 **+6.8%**，長期不衰減；58 人中 51 人正向。
- **Lemus & Marshall (2020, Kaggle 研究 + RCT)**：實時公開榜令提交量 **+21%**、最高分 **+1.7%**。
- **Steffen & von Bieberstein (2018, 瑞士鐵路餐飲 RCT)**：實時顯示「同事平均銷售」→ 營業額 **+3.3~3.8%**；效果**主要來自略低於平均的中間層**。
- **Delfgaauw et al.（荷蘭零售連鎖 128 店）**：每週把 5 間同級店的銷售增長排名貼出 → 銷售增長 **+5 個百分點**；再加獎金**沒有額外效果**。

### 支持「不應給全場精確名次」的證據

- **Barankay (2012)**：1,754 名銷售員、3 年 RCT。**移除**排名資訊令銷售 **+11%**；機制是「得知排名比預期差」的 **demoralization（洩氣）效應**。關鍵補救：**加入「達到 top 10%/25%/50% 所需的銷售額」門檻（即「要追多少才追得上」）可消除洩氣**。伴隨研究：被告知排名的人**更不願回來工作**。
- **Bandiera, Barankay & Rasul**：水果採摘隊張貼排名 → 生產力**下降 14%**；但加入錦標賽獎金則 +24%。
- **Eriksson, Poulsen & Villeval (2009)**：持續告知對手表現 → **最差表現者分數下降**，最好表現者不受影響。
- **N-effect（Garcia & Tor, 2009）**：競爭者數量越多，競爭動機越低。**2,000 人的池子本身就是動機稀釋器**。
- **最後一名厭惡（Kuziemko et al., 2014）**：人對「最後一名」有特別強烈的厭惡。→ 公開底層名次是傷害最大的資訊。
- **Superstar effect（Brown 2011；Deutscher et al. 2023）**：場中存在壓倒性強手時，其他人的努力與勝率下降，**對高水平者影響最大**。
- **Park & Kim (2021, JMIR Serious Games)**：只有 macro（全體）榜時，**中上層體驗成功、下層體驗失敗**；建議同時設計 macro + micro 榜。
- **Kahoot 文獻回顧（Wang & Tahir, 2020，93 篇）**：整體學習效果正面，但學生報告「不能改答案、時間壓力、怕輸、追不上」。
- **Choking under pressure（Beilock & Carr 2001；DeCaro et al. 2011）**：對已自動化的技能，壓力下的「自我監控」會打斷自動化流程。打字正是高度自動化的技能——呢個係「實時名次會分心」嘅理論依據（**屬機制推論，未有打字比賽的直接實驗**）。

### 調節因素（最重要嘅設計啟示）

1. **位置決定效果**：中間位置最有反應，落後太遠與領先太遠都會放鬆。→ 要顯示「附近的人」而不是「頂端」。
2. **可達性決定是否洩氣**：Barankay 的 path-goal 結果——只要告訴人「還差多少」，洩氣效應消失。
3. **參考組大小決定動機**：小池（Duolingo 30 人、TypeRacer 10 人）有效；大池無效。
4. **固定文章的比賽無處可逃**：只有「繼續打」或「放棄」，所以洩氣風險**比多任務環境更高**。

## C. 本場景（2,000 人、手機/電腦分組、全球遠程）的特殊考量

**(a) 手機組士氣**：分組排名本身已是正確的第一道保護。但手機組若看到「2,000 人中的第 1,780 名」，等於每天都被告知自己是「後段班」。**建議：手機組只給百分位區間與追趕提示，不給精確名次。** 兩組榜單不應同屏出現。

**(b) 作弊與干擾**：
1. **即時校準迴路**：自動打字腳本可以看着實時榜確認自己是否已領先，即時調整輸出速率。
2. **反作弊要靠事後審核**：TypeRacer 對 >110 WPM 觸發驗證；實時榜若把可疑帳戶即時公開展示，會令審核更難做。
3. **公開顯示名稱的審核負擔**：實時榜會把名字即時展示給所有人（Kahoot 因此提供自動暱稱選項）。
4. **針對性騷擾/stream sniping**：實時榜會放大「誰領先」的可見度。

**(c) 技術成本與可擴展性**：全量廣播確實不可行（4,000 × 2,000 = 800 萬次/秒）。但**低頻聚合榜的實際成本極低**：
- 聚合：每 1–2 秒 flush 一次，用 Redis ZSET pipeline 每次約 2,000 次 `ZINCRBY`，峰值提交 10,000/秒亦只是同一 batch 內更大增量，**不增加任何扇出**。
- 發布：每 3–5 秒向 2,000 條連線廣播一份摘要 → 約 **400–670 條訊息/秒**、每條 1–5 KB → **< 3 MB/s**。單一 WSS 節點即可；甚至可以用 CDN 快取一個每 5 秒更新的 JSON 讓前端輪詢。
- 自己名次：`ZREVRANK` 每 10 秒一次 = 200 QPS，可忽略。
- **關鍵紀律：榜單計算絕不能進入提交路徑。** 提交只回本人（維持 p95 ≤100ms），榜單走另一條低優先級通道。
- 先例：Kahoot 單場 2,000 人（高階方案），世界紀錄 4,092 人；Lichess 一場數千人的實時榜。**2,000 人的實時聚合榜在技術上不是難題，難題是產品設計。**

**(d) 適合 vs 不適合實時顯示**

| 適合（低風險、有動機價值） | 不適合（高風險、低價值） |
|---|---|
| 自己的已用時間、已提交音節數 S/N、進度條、當前速度、準確度、試算分 | 全場逐名次的實時跳動 |
| 自己的**百分位區間**（「你在前半 / 前 25%」） | 精確名次數字（尤其後段與最後一名） |
| 本組 **Top N**（每 5–10 秒，可展開） | 他人的逐字/逐題詳細成績 |
| **與上一名次的差距**（差幾個音節 / 差多少速度） | 跨組（手機 vs 電腦）混合排名 |
| 「剛剛超越 X 人 / 被 X 人超越」的 delta 提示 | 把名次放在打字區正中央 |
| 已完成人數、完成率（社會證明，壓力較低） | 落後者的「還差 N 名」精確距離（若無法顯示差距） |

## D. 推薦的實時信息顯示方案

### 方案總體：三層顯示

**第 1 層｜主顯示（永久、本地即時、零網絡依賴）**
自己的已用時間、S/N、進度條、當前速度、準確度、試算分。

**第 2 層｜低頻比較（每 3–5 秒，本組限定，可一鍵隱藏）**
- 自己的**百分位區間**（分段顯示：「前 10% / 前 25% / 前 50% / 後半」），**不顯示精確名次數字**。
- 本組 **Top 10**（顯示名稱 + 完成百分比或當前速度），預設收起、可展開。
- 已完成人數 / 總人數。

**第 3 層｜追趕提示（每 5–10 秒，自己視角）**
- 「距離上一個名次還差 X 個音節 / 需要再快 Y 音節每分鐘」——Barankay path-goal 發現能消除 demoralization 的關鍵元素。
- 「你剛剛超越了 N 人 / 被 N 人超越」的短提示。

### 具體參數建議

| 項目 | 建議 |
|---|---|
| 更新頻率 | 聚合 flush 每 1–2 秒；對外摘要每 **3–5 秒**；只在內容變化時推送 |
| 只限本組 | 是。手機組、電腦組各自一個榜；**絕不同屏混合** |
| 精確名次 | 比賽中**不公開**他人精確名次；自己的精確名次可每 10 秒私下顯示（可關） |
| 可選性 | 提供「專注模式」隱藏第 2、3 層；預設開啟第 2 層、關閉 Top 10 展開 |
| 文案 | 明確標示「即時榜僅供參考，最終名次以完場結算為準」 |
| 反作弊 | 異常速度/間隔的帳戶先隔離再審核，不即時公開展示其名次 |

### 完場榜單

- 完場即顯示**兩組完整榜**（分頁、可依綜合分/速度/準確度排序），自己的名次高亮，附前後對手。
- 完場榜與比賽中的即時榜**必須由同一份持久化提交記錄重新結算**，避免 ICPC freeze 式的「最後一刻名次大變」。

### 技術實現建議（對應 SPEC §7.3）

1. **提交路徑不變**：每次提交/撤回只回本人，不觸發任何榜單扇出。
2. **聚合層**：每（場次, 組別）一個 Redis ZSET；聚合 consumer 每 1–2 秒 pipeline `ZINCRBY`。
3. **發布層**：每 3–5 秒產生一份摘要（Top 10 + 百分位桶邊界 + 完成人數），經 WSS 廣播；可再加 5 秒 CDN 快取 JSON。
4. **自己名次**：每 10 秒 `ZREVRANK`（約 200 QPS）。
5. **一致性**：榜單容許 3–5 秒延遲；正式成績仍以伺服器持久化的提交記錄為準，完場重新結算。
6. **容量結論**：2,000 人規模下，一個 Redis 實例 + 一個 WSS 節點已足夠；真正的容量瓶頸在提交持久化，不在榜單。

### 落地順序與驗證

- **第一版（維持 spec 現狀 + 小幅加值）**：只做第 1 層 + 完場榜。零新增同步成本。
- **第二版（建議在彩排後）**：加第 2 層與第 3 層。彩排做三組比較（無比較 / 只有百分位 / 百分位+Top10+追趕提示），量度：**完成率、放棄率、最後 25% 的提交速度變化（檢測 demoralization）、完場問卷**。按名次分段看效果。
- **活動形式決定強度**：輕鬆聯歡型 → 只用第一版；競技型 → 用第二版，並考慮把最後 10–15% 的時間改為「凍結式」呈現，保留懸念。
