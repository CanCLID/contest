# Issue #1：研究数据采集目标与当前系统的差距

评估日期：2026-10-27（香港时间）

代码基线：`main`，`90a3a01aec06e8698ce0e8c0c175ed8157fc77c9`

需求依据：[CanCLID/contest issue #1](https://github.com/CanCLID/contest/issues/1)，此前读取的正文更新时间为 2026-10-26。

文档性质：当前实现的差距分析及后续建议；不表示下面的建议已经实现或获定案。

## 结论与评估范围

目前已有可复用的游戏输入界面和部分过程日志，但距离 issue #1 的完整研究采集系统仍有较大差距。现阶段适合开发试采、验证数据格式，尚未达到约 1,000 人正式研究采集的条件。

Issue #1 以不同粤语、识字、粤拼和键盘背景参与者的无调粤拼产出、修订和练习数据为核心，支持拼写困难、自我修正、重复题与新题表现，以及已知文本条件下的纠错和解码研究。比赛成绩只能覆盖其中一部分。

现有输入前端可以继续使用。主要待补的是研究任务流程、纵向身份和背景信息、跨模式事件记录，以及可靠采集与保存。约 2,000 人同步比赛、管理端、认证和正式排行榜属于另一个需求范围，不作为本报告衡量 issue #1 完成度的标准。

## 已有基础及其局限

### 三轮游戏的过程日志

三轮已具备一部分可用于研究的原始观察：草稿修改前后内容、输入来源、提交原串、大小写、部分原生输入与 composition 标记、事件序号和相对时间。词链及篇章撤销后，历史提交事件仍保留，因而可以在记录完整时重建首次提交和修订答案。

目前仍有以下限制：

- 共享日志只有轮次、seed、开始时间等基础字段，没有统一的参与者、会话、题目 encounter、研究阶段或背景问卷版本。
- 词链导出使用 `inputEvents`／`droppedInputEvents`，另外两轮使用 `events`／`droppedEvents`，导出格式尚未统一。
- 选区、失焦、页面可见性等事件在各轮覆盖不一致；实际设备、键盘设置、指令语言和指令版本没有形成统一记录。
- 日志主要先累积在内存，完场后才保存最近十轮。刷新、关闭或放弃可能丢失本轮，造成只保留完成者数据的偏差。
- 已有每轮 20,000 事件及 4 MiB 上限、截断标记和缺失计数；分析时仍需单列或排除不完整记录。
- 落石已经提交的字不能重新打开修改；研究任务要求的可重开操作需单独设计。

代码依据：[共享日志](../demo/games/free-input.mjs)、[词链导出与撤销](../demo/games/chain/chain-dom.mjs)、[落石记录](../demo/games/rocks/rocks-dom.mjs)、[篇章记录](../demo/games/ghost/ghost-dom.mjs)。

### 全站练习历史尚未接通

单篇自由练习完场主要保存昵称、组别、文章标识、对错总数、耗时及 `hintsUsed`。它没有持久保存完整原始回答、草稿编辑和撤回历史。

声韵塔并非没有数据：它保存最多 500 条答案日志和 100 轮结果。但每条答案主要是汉字、参考答案、实际答案和对错，缺逐项时间、编辑过程、提示曝光、题目 encounter 及完整抽题过程存档。因此还不能和三轮日志组成同一参与者的完整学习轨迹，也不能可靠标注“新题／重复题”或练习间隔。

代码依据：[单篇 `completeRound`](../demo/app.mjs)、[声韵塔 `submitAnswer` 与 `toSaved`](../demo/games/tower/tower.mjs)。

## 三个影响研究解释的关键区别

### 关闭提示不等于无反馈初测

当前错答后仍会显示正误、改错对照和准确率。参与者随后修改时已经获得反馈，不能直接归为独立自我纠正。游戏中的“上次提交”面板也不等于 issue 要求的无反馈自查。

单篇目前主要记录本轮是否曾开过提示，没有记录每次开关的时间、受影响题目、提示持续开启时新出现的答案，以及每次揭示前的回答状态。后续需要记录实际展示内容和时间；展示日志只能说明内容曾可见，不能证明参与者阅读或理解了它。

代码依据：[单篇 `submit`、`renderReading` 和提示开关](../demo/app.mjs)、[词链改错面板](../demo/games/chain/chain-dom.mjs)。

### 游戏评分不能直接作为研究中的拼写准确率

落石超时按赛规计错，但研究中应与“提交了错误拼写”分开。首次提交、无反馈自查、反馈后修改和最终保留答案也应分别计算，不能只使用完场准确率。

参考答案和可接受异读还需校对。现有词链题库每位置使用单个读音字符串，各小游戏题库明确标为未经完整人工校对；自动声韵拆分也不能替代研究所需的人工复核特征标注。

代码依据：[落石漏接计分](../demo/games/rocks/rocks.mjs)、[词链题库](../demo/games/chain/data.mjs)、[落石题库](../demo/games/rocks/data.mjs)、[示范篇章](../demo/questions.mjs)。

### 连打切分与时间属于不同层次的记录

例如 `hoenggon` 是真实输入观察；把它分成两个音节，是根据参考答案、编辑距离和 Yune 推定的评分注释。推定字数、音节边界、空跨度漏字和逐音节错误数都不能直接当成参与者亲自提供的边界或意图。原始输入应保留，研究注释应允许复核和重算。

同一批提交中的全部音节共用提交时间，不能据此声称已经获得逐音节反应时间。词链事件使用 `performance.now`，落石和篇章主要使用 `Date.now`，时间记录也还需要统一。

当前记录的是浏览器可以观察到的文本变化与部分按键事件，并非完整物理按键流；尤其不能假定一次手机文本变化等于一次物理按键，也不能将 `g → go → gon → gong` 这样的正常构词过程逐步算作拼写错误。

代码依据：[切分及评分策略 `gradeConfirmedInput`](../demo/games/free-input.mjs)、[篇章批量提交时间](../demo/games/ghost/ghost-dom.mjs)。

## 自由输入与 issue 任务定义的关系

当前自由输入有价值，应该保留。它推进了 issue §8 所描述的真实连续词组输入数据采集能力，能够保留参与者实际输入的连续原串，而不是事后拼接逐音节记录。

不过，issue 核心任务仍写着逐音节提交，§8 是指定整词一次提交；当前游戏允许自由混合提交，属于另一种任务条件。现有功能尚不等于已经实现了 §8 的独立研究任务。

建议比赛继续自由输入，另外增加简短研究任务，明确记录提交粒度、时间压力、分界提示和反馈条件。若决定让核心研究任务也采用自由长度提交，应同步修改研究协议及分析口径。无论采用哪一种，都不应把不同条件直接混合分析，也不需要为了研究将三个比赛环节重新改回强制逐字确认。

现阶段数据适合定位为“已知汉字提示下、游戏条件中的无调粤拼输入与修订数据”。它可以支持有关拼写与修订的探索，但不能直接测量声调拼写、口语发音或输入法候选交互，也不能仅凭修订串判断错误来自手误还是知识不足。

## 建议的实施顺序与验收重点

以下是后续建议，尚未实现。

| 顺序 | 要补的工作 | 验收重点 |
| --- | --- | --- |
| 1. 统一采集基础 | 稳定参与者／会话／题目 encounter／阶段编号、带日期背景信息、统一全模式事件格式、途中保存、批量上传和确认 | 任意一名参与者中断、撤回、重进或切换模式后，仍能关联原始记录；首次答案不被后续修订覆盖，缺失有明确标记。 |
| 2. 建立研究任务流程 | 先补无反馈 B 初测与自查，再接入反馈练习、重复题及新题后测；补独立 A 抄写、C 听音，以及不会／跳过 | 初测和自查结束前不泄露正确性；记录每阶段保留答案、准确曝光、音频交互及跳过／未完成状态；抄写题单不提前泄露初测答案。 |
| 3. 校对题库并试采 | 人工校对参考答案及异读，建立锚定题、拼写特征标签、配对和轮换列表；邀请不同语言、识字与粤拼背景参与者试采 | 能完整重建输入、反馈曝光及练习历史；检查疲劳、跳过、音频失败、手机事件完整性和不同背景组的可完成性，再扩大到约 1,000 人。 |

比赛系统和研究系统可以共用输入组件，但需分别定义计分规则与研究指标。现有比赛后端规划以提交、撤回和计分为主，研究事件的保存与分析层仍需设计；保存完整过程不要求每次按键单独发网络请求，可以在本地记录后有界地合批上传。

重复题进步与新题表现应分别报告。上述流程可以支持描述学习轨迹；若要把改善归因于某种教学方法，还需要合适的比较设计。
